# 咖啡馆 AI NPC 项目：总体设计与开发遵守规范

**版本：v1.0｜日期：2026-09-30｜适用：Godot 4.7.x + GDScript + Python Harness + 大模型 + SQLite**

> 先确认需求，再查已有实现；能用内置能力就不另找框架，成熟组件合适就直接复用；只编写当前体验缺少的业务逻辑，不为假设中的未来建设平台。

本规范适用于人类开发者与 AI 编程助手，配套《Harness 与大模型接入主线功能方案 v0.3》和《Godot 4.7 咖啡馆 NPC 3D 前端开发方案 v0.1》。它约束实现方式，不增加产品范围，也不要求推倒已正常工作的实现。

**本项目的交付物是可体验的角色，不是一套通用游戏引擎、通用 Agent 框架或插件平台。**

文中的插件与资料经过公开文档核查，但未在本项目中安装、运行或联调。候选清单不等于兼容性认证，也不等于必须安装的依赖清单。此前方案中的代码片段是参考，不能绕过本规范直接当作唯一实现。

## 1. 不可变的项目边界

### 1.1 主线能力不能以“简化”为由删除

必须保留环境感知、情境理解、持续战略目标、事件决策、状态转移、多人对象区分、玩家跨会话记忆、记忆纠正、正常暂停与继续、实际 3D 动作，以及真实大模型接入。

规则替身、占位模型和脚本配角可以用于分步联调，但不能用它们替代最终应交付的模型决策、记忆和互动能力。美术可以简化；“走到设施”“拿放杯子”“下次继续话题”等真实功能不能退化成台词描述。

### 1.2 当前原型的范围

一个咖啡馆、一位老板娘、2～8 个固定测试身份；一个 Godot 进程管理一份共享 3D 世界，一个 Python 进程维护 NPC 运行时，SQLite 保存跨会话所需资料。

当前不建设账号系统、真实多客户端联网同步、多房间服务、安全治理、事件重放、容灾恢复、分布式一致性、审计平台、灰度发布或容量治理。不因某个插件附带这些能力，就把它们变成开发任务。

保留简单错误提示、动作结果、状态条件和异步调用，因为缺少它们会直接破坏互动。插件演示和功能测试不属于历史事件重放系统。

### 1.3 一句话判定新增工作

新增模块、依赖、配置或抽象之前，回答：

**“它具体让哪一个已确认的玩家行为能够发生，或解决了哪个已经观察到的主线问题？”**

只能回答“以后可能需要”“大项目都这么做”“架构更专业”的，暂不实现。YAGNI 也不意味着不整理代码，而是不提前实现尚未需要的能力。[R24]

## 2. 开发前必须先做复用判断

### 2.1 检索顺序

| 顺序 | 先检查什么 | 处理原则 |
| --- | --- | --- |
| 1 | 当前工程已有场景、脚本、依赖、组件和历史选型记录 | 已满足需求就继续用，不平行新建同类实现 |
| 2 | Godot 内置节点、编辑器功能；Python 标准库和已引入库 | 内置能力够用时，可以直接结束插件调研 |
| 3 | 官方示例、官方教程与作者提供的参考工程 | 复用对应版本的必要部分，不整包带入无关玩法 |
| 4 | 官方插件目录、维护者仓库、成熟第三方库与资产包 | 比较真实适配成本，先验证再决定采用 |
| 5 | 小范围业务实现 | 只补现有能力的缺口，不从头重建底层系统 |

**先检查项目，再检查内置功能，再检查外部生态。不要把“先搜索插件”误解成忽略项目已经拥有的实现。**

没有源码访问时，明确写“未检查工程”；只能基于已提供设计提出建议，不能声称已经发现重复代码或完成集成。

### 2.2 哪些任务需要重新检索

首次增加寻路、相机切换、状态图、对话编辑、动画控制、模型接口、记忆检索、测试工具等可复用能力时，必须做检索。

修改一条文案、调整已经验证的速度参数、修正当前函数的小错误，不需要重新进行全网选型。相同版本与相同需求可以复用已有结论；版本、需求或限制有实质变化时再核查。

有歧义时，先确认实际需求。例如“NPC 记忆”可能需要的是保存话题进度，而不是向量数据库；“动作系统”可能需要的只是播放预制动作和等待结束，而不是行为树编辑器。

### 2.3 如何搜索，而不是只搜一个产品名

先把问题翻译成已有生态使用的术语，例如：

```text
Godot 4.7 third person camera follow transition
Godot 4.7 NavigationAgent3D navigation demo
Godot statecharts parallel states pause
Godot dialogue runtime external text
Python sqlite3 player memory topic progress
```

搜索结果只用于找入口。功能和兼容性判断回到官方文档、原作者仓库、具体 Release 和示例。不要把镜像仓库、博客搬运或 AI 生成的摘要当成最终依据。

一般先看一个内置方案与一到两个最相关候选。已有方案满足当前验收、没有阻断条件时就停止检索，不为补齐列表继续研究十几个同类产品。已经明确的内置解法不要求凑够候选数量。

### 2.4 复用结论只需一张小卡片

首次引入通用能力、增加依赖或决定自研时，记录以下内容；放在现有任务说明或开发记录中即可，不强制新增一套文档系统。

```text
功能与可见验收：
工程内现有实现：
内置方案／外部候选及原始来源：
目标引擎、插件版本与实际测试平台：
结果：直接复用／小范围适配／暂不引入／自研缺口
理由：当前哪里适合、哪里不适合
验证：仅阅读／演示运行／场景接入／目标平台导出
本次不做：
```

“暂不引入”可以是正确结论。不要为了满足规范而购买插件、引入收费服务或增加运行时依赖。

## 3. 如何判断现有方案是否值得采用

### 3.1 看实际匹配，不看功能数量或星标数量

| 判断项 | 要核查的问题 |
| --- | --- |
| 核心功能 | 它是否覆盖本次真正需要的行为，而不是只提供相似名称？ |
| 集成方式 | 能否接收现有数据、返回所需结果，还是强制重写项目结构？ |
| 版本与平台 | 选定版本是否覆盖 Godot 4.7.x、实际桌面平台、语言和渲染方式？ |
| 可验证性 | 是否有清楚的文档、可运行示例、安装步骤和发布记录？ |
| 已知限制 | 当前功能相关的 Issue、迁移说明和限制是否构成阻断？ |
| 总成本 | 配置、适配、依赖和理解成本，是否低于小范围自写？ |
| 资源许可 | 实际使用的代码、模型、贴图和示例素材分别采用什么许可？ |

成熟不是“最近每天都有提交”，也不是“功能很多”。稳定小组件可能很久不更新；高活跃项目也可能不适合当前需求。

代码许可不能自动代表演示素材许可。例如 LimboAI 仓库分别说明了代码与标志、示例美术的许可；选用时应保留对应说明，不把整个仓库视为同一种授权。[R14]

### 3.2 版本验证必须具体

项目固定实际安装的 Godot 4.7.x 补丁版本和对应导出模板，查阅 4.7 文档。官方归档确有 4.7.2 stable，但是否升级以当前工程需求为准，不能为了“最新”频繁改变基线。[R01]

插件记录具体 tag 或固定提交，不以 `main/master/latest` 作为长期基线。Godot 官方示例仓库说明：`master` 对应引擎开发分支，稳定版应查对应分支，不能无条件复制最新示例。[R02]

“Godot 4+”“最低 4.3”只说明声明范围，不证明本项目精确组合已经通过。原生扩展还要确认本次实际导出目标是否有对应构建；不要求测试当前未计划的平台。

如果 README、版本表与 Release 信息不一致，记录冲突，检查所选发布包及其文档，不自行补出兼容结论。

### 3.3 先验证一条最小功能，再接入项目

插件验证只围绕本次需求。例如相机插件验证“玩家跟随 → 对话镜头 → 返回”；状态插件验证“开始动作 → 暂停 → 继续 → 结束”；对话插件验证“显示实际后端文本 → 收集选项 → 返回现有会话”。

对需要随桌面 Demo 分发的运行时插件，再验证一次当前目标平台导出。纯编辑器工具不要求导出为游戏运行时。

应区分：**文档确认、示例跑通、项目接入、导出通过**。只读了 README，就只能报告文档确认；编辑器不报错不代表目标行为已经实现。

### 3.4 自研的合理范围

可以自写：稳定 ID 到场景节点的映射、角色目标选择规则、咖啡馆菜单、少量状态转移、玩家话题进度、三组 Prompt、现有接口间的字段转换，以及插件没有覆盖的小段业务逻辑。

默认不自写：3D 寻路算法、碰撞求解器、动画混合器、骨骼挂接系统、WebSocket 协议栈、通用状态图编辑器、通用对话语言、数据库引擎、通用测试运行器。

**手写一个咖啡制作的有限业务流程不是重复造轮子；为它写一个通用工作流引擎才是。**

## 4. 本项目的复用地图

本节是已核查的优先检索入口。处理建议属于本项目设计判断；官方能力与版本信息在对应来源中核查。所有候选的本项目运行状态均为“未验证”。

### 4.1 优先复用 Godot 内置能力

| 需求 | 优先使用 | 本项目应该写的部分 | 不应再写的部分 |
| --- | --- | --- | --- |
| 玩家／NPC 运动与碰撞 | `CharacterBody3D` [R03] | 输入、速度、转向与目标跟随 | 自建角色物理解算器 |
| 前往咖啡机、桌旁等站位 | `NavigationAgent3D` 与烘焙导航数据 [R04] | 语义锚点映射、物理步移动、到达反馈 | Python 再算一份路径，或新写寻路算法 |
| 基础第三人称镜头 | `Camera3D + SpringArm3D` [R05] | 当前相机参数、控制身份切换 | 从头开发完整镜头框架 |
| 行走、说话与动作混合 | `AnimationPlayer + AnimationTree` [R06] | 动画名映射、当前动作参数和通道约束 | 自建动画图或混合求解器 |
| 头部看向玩家 | `LookAtModifier3D` [R07] | 骨骼配置、目标选择、转动幅度 | 为普通注视自写完整 IK 系统 |
| 进店、离店与交互范围 | `Area3D` [R08] | 区域含义、事件对象和触发去重 | 自建空间触发器系统 |
| 杯子跟随手部骨骼 | `BoneAttachment3D` [R09] | 拿起／放下时机、道具插槽 | 每帧手算一套骨骼跟随 |
| 与 Python 通信 | `WebSocketPeer` [R10] | JSON 消息、动作 ID、反馈映射 | 重写 WebSocket，或强行实现引擎私有协议 |
| 可调场景与动画配置 | `Resource`、导出属性 [R11] | 当前项目真正需要的参数 | 通用配置语言、配置编辑器平台 |

**内置能力也有使用条件。** `NavigationAgent3D` 负责提供路径相关计算，不自动替角色完成运动；不可把“导航结束”一概当成“目标已到达”。其 4.7 文档还标有 Experimental，应固定版本并验证实际需求，而不是因此直接重写寻路。[R04]

复用的结果通常是“引擎能力 + 一小段业务脚本”，不是“安装后零代码”。

### 4.2 第三方插件：按触发条件采用，不批量安装

| 候选 | 已核查能力／来源 | 何时值得采用 | 当前边界 |
| --- | --- | --- | --- |
| **Phantom Camera** | 跟随、注视、优先级和镜头过渡；提供 3D 示例。[R12] | 已明确需要多组对话镜头、群体构图或复杂切换 | 基础跟随足够时先用内置组合；采用后不能再让另一脚本同时控制同一相机变换 |
| **Godot State Charts** | 状态图、条件转移、延迟转移和调试视图；仓库提供文档、示例与测试。[R13] | 本地动作出现嵌套／并行状态，或确实需要可视化组织 | 少量线性步骤可以保留明确状态和普通函数；不为几种状态强装插件 |
| **LimboAI** | 行为树与层次状态机，提供 GDExtension／模块两类接入及兼容表。[R14] | 确有大量可复用本地行为，或设计人员需要行为树编辑 | 不接管 Python 的战略和记忆；先核对所选发行版构建，不为一个 NPC 先编译自定义引擎 |
| **Dialogue Manager** | 当前仓库提供面向 Godot 4.6+ 的 Dialogue Manager 4，是分支对话编辑器与运行时。[R15] | 固定教程、对白内容和分支明显增多，需要编辑工作流 | 动态聊天先验证是否值得适配；不能复制一套后端会话和玩家记忆到插件中 |
| **GUT** | GDScript 测试框架；版本表列出 9.7.1 对应 Godot 4.7.x。[R16] | 需要自动验证动作、会话与桥接脚本 | 使用对应版本，不新写测试框架；未在本项目执行 |
| **GdUnit4** | 支持脚本及场景测试；版本表含 4.7 系列条目。[R17] | 现有团队已使用，或其场景测试方式更符合需求 | 与 GUT 默认择一；不要把 4.7／4.7.1 条目直接写成 4.7.2 已验证 |
| **Kenney Furniture / Food Kit** | 官方页面提供 3D 家具和食物资源，标注 CC0。[R18] | 用于咖啡馆测试场和道具占位 | 导入后检查尺寸、原点、碰撞、外观；不假设自带本项目需要的动画或设施逻辑 |

补充核查：Phantom Camera 的 v0.11.0.3 发布说明包含 Godot 4.7.1 相关修复及额外注意事项，说明只看“支持 Godot 4”不够。它是版本核查的例子，不代表本项目已测试该版本。[R12]

状态图与行为树插件不是越多越好。**对同一组本地动作，默认只选一种组织方式；不能让 State Charts 和 LimboAI 同时掌控同一状态。** 动画状态与业务状态属于不同语义，可以各自存在，但要明确谁发出意图、谁报告结果。

### 4.3 后端同样遵循复用优先

| 需求 | 已有能力 | 本项目处理 |
| --- | --- | --- |
| WebSocket 服务 | FastAPI 官方 WebSocket 支持 [R19] | 使用现有服务，不为一个入口新增网关框架 |
| 进程内事件队列 | Python `asyncio.Queue` [R20] | 一条简单队列与明确回调，不建设 Actor 平台或消息中间件 |
| 模型 HTTP 调用 | 当前供应商官方 SDK，或已有 HTTPX 异步客户端 [R21] | 二者选一个；已有 HTTPX 满足需求就保留，不重复包三层客户端 |
| 模型输出结构 | Pydantic 类型校验 [R22] | 声明本项目输出结构，不自建 Schema 语言和反射系统 |
| 跨会话记忆存储 | Python `sqlite3` [R23] | 直接保存偏好、经历、进度、承诺，不自研数据库封装平台 |
| Agent 编排 | 可先核查 LangGraph 等现成方案；其官方定位包括长时、有状态编排 [R25] | 本原型没有因检查点／耐久执行而引入它的必要；不要为了不用框架而重新实现同等通用平台 |

最后一行不是宣布框架“不好”，也不意味着已有正常使用的框架必须移除。判断对象是当前工程的实际净收益。记忆框架和向量库也遵循同一规则：先确认当前缺口，再比较，不能因为项目叫“Agent”就默认安装。

## 5. 防止过度设计：只交付当前需要的能力

### 5.1 先完成纵向功能，再扩充横向通用性

每个开发任务应连通一条可观察链路，而不是只完成一批空接口。

| 任务 | 应当交付 | 不应先做 |
| --- | --- | --- |
| NPC 走到咖啡机 | 实际路径、运动、到达结果，后端能收到 | 多层路径服务、开放世界导航管理 |
| 多人聊天 | 明确发言对象，保留待答问题，一份共享 NPC 状态 | 通用社交网络、任意规模房间系统 |
| 下次续谈 | 当前进度保存，同一玩家回来后能够接上 | 分布式记忆、知识图谱平台 |
| 动作暂停 | 当前动作停下，继续后按有效阶段推进 | 通用事务补偿、可恢复任务编排平台 |
| 调试 NPC | 一块面板显示观察、目标、动作、记忆引用 | 独立日志检索、指标和审计平台 |

不能把 `TODO`、返回固定成功、瞬移、隐藏错误或一句“我记住了”作为功能完成依据。

### 5.2 配置只服务已有的变化

速度、交互距离、动画映射、模型地址、模型 ID 和 Prompt 适合配置。没有实际使用者的能力开关、多供应商自动路由、动态插件发现、任意图执行语言不预留实现。

在多个设施有相同交互结构时，可以复用一个场景或组件；只有一个咖啡机时，不需要提前建立可表示任何设备的工业流程 DSL。

### 5.3 性能优化必须有当前问题

先用当前场景验证模型延迟、帧率和动作连续性。发现具体瓶颈后，使用已有分析工具定位并修改相关位置。

不提前引入对象池、复杂缓存、多线程任务平台、增量同步或 C++ 重写。但不能把已出现的卡顿说成“原型不用管”。正确做法是解决实际问题，不扩展成性能基础设施项目。

### 5.4 不因候选插件扩大范围

插件支持联机，不代表本项目要联机；支持复杂过场，不代表需要过场导演工具；支持持久执行，不代表恢复整个运行现场成为必须。

每个新增依赖都应替代一段本来要维护的能力，或解决一个已确认功能。只增加一套概念而没有减轻当前工作，不采用。

## 6. 防止过度抽象：先理解变化，再设计接口

### 6.1 默认使用具体、可读的实现

函数能表达的逻辑，不必创建类；一个职责清楚的类能表达的逻辑，不必拆成多层 Service／Manager／Provider。

方案中的模块名表示职责，不意味着每个名字都必须生成一个接口、基类、实现类、工厂和注册表。可以从少量文件开始，按真实变化拆分；不能把“少量文件”实现成所有功能共用一个巨型脚本。

### 6.2 抽象需要回答一个具体问题

新增接口、基类或适配层时，至少说明它解决了哪一种已存在的需求：真实重复、明确的外部系统边界、确实需要替换的实现，或当前测试隔离。

只有一个实现并不自动禁止接口。例如模型网关和 Godot／Python 桥接就是明确边界。但它们应当很薄，不继续叠加工厂、注册中心和多级 Provider。

### 6.3 去重的是同一知识，不是外观相似的代码

两个“确认／取消”按钮不一定属于同一业务。取消订单和暂停话题的状态含义不同，不应强行合成 `UniversalTransactionHandler`。

相反，两个位置各自定义同一杯子的归属、同一承诺的完成规则，属于应消除的重复事实。

少量相似代码在边界尚不清楚时可以暂时存在；当确认它们遵守同一规则且需要同步变化，再提取共用部分。不机械执行“三次重复就抽象”，也不以此允许复制权威业务规则。

### 6.4 具体反例

| 合理实现 | 应避免的实现 |
| --- | --- |
| `npc_motor.gd` 调用导航和角色运动组件 | 自建跨引擎 MovementProvider / PathService / MotorFactory |
| 一个薄 `ModelGateway` 封装当前供应商请求 | UniversalProviderFactory → AgentRouter → GenerationService → Adapter |
| 用 `Resource` 保存实际动画名称与参数 | 为配置再设计通用 DSL、解释器和编辑器 |
| 枚举与明确步骤控制简单动作 | 为五个阶段写一套通用状态图框架 |
| 复杂本地状态直接选用现有状态图插件 | 先复制插件能力，再包装成自己的框架 |
| `MemoryService` 提供玩家资料与进度读写 | 为 SQLite 四张业务表建立通用存储插件体系 |
| 场景根节点注入引用并连接信号 | 通用依赖注入容器、服务发现和全局注册中心 |

### 6.5 封装不能只负责转发

若连续数层只把相同参数传给下一层，没有表达规则、适配外部差异或隔离必要依赖，应合并。

不要为“不泄露引擎类型”而复制 `Vector3`、节点、信号和资源体系。本项目明确使用 Godot，只有实际跨 WebSocket 的数据才需要序列化成约定格式。

## 7. 防止前后端重复实现同一职责

### 7.1 每个状态只有一个主要维护位置

| 信息／流程 | 主控位置 | 其他部分的角色 |
| --- | --- | --- |
| 位置、碰撞、导航、杯子实体与插槽 | Godot | Python 接收观察和执行结果 |
| 目标、话轮、会话、完整技能流程 | Python Harness | Godot 展示并执行单步动作 |
| 玩家偏好、共同经历、话题进度和承诺 | Python + SQLite | Godot 查询、显示、发送玩家修改意图 |
| 动画、镜头和局部动作表现 | Godot 内置系统或所选插件 | 后端发送表达和动作意图 |

Godot 接入后，不再保留 Python 离散世界作为另一份实际位置控制器。若仍需用于测试，必须明确它是独立替身，不与 Godot 同时写同一个运行世界。

完整 `prepare_and_serve` 流程由 Python 负责；Godot 可有“制作动作开始／播放／完成”等局部状态，但不再复制“给谁做、下一单是谁、取消后接待谁”的流程。

### 7.2 插件不得成为隐含的第二个“大脑”

使用 LimboAI 或 State Charts 时，只放入已经划给 Godot 的局部动作控制。不要让插件自行决定邀请对象、读取另一份玩家记忆，再与后端相互竞争。

使用 Dialogue Manager 时，先明确固定内容与后端动态会话的边界。聊天 UI 不应把全部 LLM 输出强制编译成一套新剧情脚本，也不能顺便维护另一份话题进度。

使用 Phantom Camera 后，镜头变换只有一个控制者；相机适配脚本传递目标和模式，不再每帧覆盖插件输出。

**复用组件不等于把项目的业务职责复制进组件。**

## 8. Godot 与 Python 的实现习惯

### 8.1 Godot：使用引擎习惯，不另造一套对象系统

使用场景组合、明确节点引用、信号和资源来组织功能；依赖在合适的场景根部接线。Godot 官方场景组织文档讨论了场景依赖和由上层协调的做法，可以作为实现参考。[R26]

业务全局单例只有确实跨场景共享时才增加，不能把每个模块都注册为 Autoload。插件要求的 Autoload 按官方说明处理，不为了符合一条机械数量限制改坏插件。

插件安装遵循官方流程与插件自己的说明，优先只导入实际需要的目录，不把测试、无关示例和整套编辑器工具自动带入运行项目。[R27]

不要同时手动播放与另一控制器争夺相同动画轨道。配置骨骼、模型正向和道具插槽，不通过不断增加修正层掩盖错误导入设置。

### 8.2 Python：普通业务程序优先

保留一个清楚的运行入口、必要队列、模型调用和存储函数。事件、战略和经历摘要可以是同一模型的不同 Prompt，不需要三个智能体平台。

JSON 结构用明确类型校验，模型提议与实际执行结果分开。出错时给出可见失败信息，不静默吞掉、无限重试或以成功占位。

当前只需少量查询时可以直接使用 SQLite 接口；如果现有工程已经采用并正常使用某个 ORM，则优先沿用，不为追求“最少依赖”进行无关重写。

### 8.3 状态检查属于主线，不是基础设施扩张

以下检查应保留：目标是否存在、动作是否还适用、玩家是否仍在场、会话是否可以继续、模型结果是否对应当前待办、所需身体通道是否可用。

它们直接避免“人已走开仍递杯”“一边暂停一边继续讲”等功能错误。不要把这些必要条件扩大成审批框架，也不要因排除安全工程而一并删除。

## 9. 对 AI 编程助手的强制要求

### 9.1 开工前

阅读当前任务相关代码、现有依赖与已确认设计。优先修改现有实现，未检查前不得宣称缺少某模块。

首次新增通用能力时完成第 2 节复用判断。需要新增主要依赖、更换基础方案、修改前后端职责或自研底层能力时，先明确收益与影响范围；普通业务修改不逐项请求批准。

不把此前 AI 生成的示例视为官方 API。核查当前版本的方法、参数、信号和插件接入方式。

### 9.2 编写过程中

只修改完成当前功能所需文件。不要顺手重命名整个项目、重排无关目录、替换正常工作的库，或为未来功能生成空类和空目录。

禁止伪造包名、插件能力和执行结果。示例缺少实际依赖时要说明；无法运行 Godot 时可进行静态检查，但不能写“场景已验证”。

禁止为了规避一个兼容问题，未经比较就开始重写插件的大部分功能。先检查版本、配置、相关 Issue 和已发布修复，再选择换用合适版本、小范围适配或缩小方案。

### 9.3 完成时

报告实际改动、复用了什么、本次自写的业务缺口、执行过的验证和仍未完成的事项。

模型输出正确、脚本解析成功、编辑器启动、桌面导出、与真实后端联调，是不同的验证层级，不能互相替代。

不得把 Mock 通过写成真实模型通过，不得把预设台词演示写成玩家记忆已经生效。

## 10. 一次开发任务的最小流程

| 步骤 | 必须产出 | 停止条件 |
| --- | --- | --- |
| 明确目标 | 一句话用户行为与可见结果 | 任务属于已确认主线 |
| 查看工程 | 找到现有落点与已用组件 | 不新建重复模块 |
| 核查复用 | 内置能力或少量候选，必要时一张小卡片 | 已有足够匹配的方案，不无限检索 |
| 最小验证 | 用所选组件走通当前最难的一个环节 | 能明确采用或放弃 |
| 场景接入 | 只写缺少的业务适配 | 实际行为进入现有主循环 |
| 功能验收 | 本次场景及受影响的相邻主线 | 没有用占位成功代替功能 |
| 清理交付 | 删除本次无用试验、记录真实验证范围 | 不残留两套活动实现 |

这是一条轻量工作习惯，不是一套审批、追踪或治理平台。不要求每个小修改都新增文档或测试框架。

### 10.1 示例：实现“老板娘走向咖啡机”

先看已有 NPC 移动脚本；检查 `NavigationAgent3D` 与官方导航示例；在目标版本验证导航数据和可到达站位；项目只补 `anchor_id → WorkPoint`、移动控制与结果反馈。

验收应看到角色沿路径绕过柜台，停在可工作的位置，后端收到实际到达事件。不得新建通用路径服务，也不得瞬移后直接返回成功。[R04]

### 10.2 示例：实现“再次到店继续上次话题”

先复用已有玩家 ID、SQLite 存储、会话状态和模型网关。确认保存的话题进度与下一次访问触发规则，再把它们接入目标生成和本轮上下文。

业务缺口是“何时提供续谈机会、拒绝后如何暂缓”，不是“再做一个记忆数据库”。若当前 SQL 与关键词检索已经支持演示，不为这个功能提前引入向量服务。

### 10.3 示例：实现“对话镜头切换”

先验证内置相机组合是否满足当前镜头；如果需要多个镜头优先级、平滑切换或群体构图，再测试 Phantom Camera。采用后替换本次重复的相机控制，而不是让两套实现同时运行。[R05][R12]

## 11. 评审只看这些实际问题

评审可以在任务说明中完成，不增加独立平台。

- [ ] 本次改动对应已确认的可见行为，没有引入非主线目标。
- [ ] 检查过已有代码和内置能力；必要的外部候选有原始来源。
- [ ] 选择插件或自研都有实际理由，不是只因为熟悉、热门或“以后可扩展”。
- [ ] 只增加当前需要的业务代码，没有空抽象、无效转发层或同功能重复依赖。
- [ ] 同一位置、任务、会话或记忆只有一个主控位置。
- [ ] 核心交互没有被删减或改成固定成功。
- [ ] 实际运行、版本与验证结果没有夸大；未运行部分明确标注。
- [ ] 使用者能用现有启动方式演示本次功能。

发现“自研引擎已具备能力”“同一功能两套主控”“空框架先行”“删除核心功能掩盖复杂度”时，应修改方案，而不是只补一段解释。

## 12. 可放入 AGENTS.md 的精简执行规则

下面是本规范的摘要，可直接并入项目现有开发说明；不需要为它再建立规则引擎。

```text
本项目只实现已确认的咖啡馆 NPC 主线：感知、战略、事件、状态、玩家记忆、3D 动作与大模型。

1. 改代码前先读当前工程，优先复用已有场景、脚本、依赖和选型结论。
2. 新增通用能力前先查内置功能、官方示例和相关成熟插件，不直接从零实现。
3. 找到足够匹配的方案即停止检索；不为每个小改动重复全网选型。
4. 优先采用总成本最低的可用方案：复用不等于必须安装插件，自研只补业务缺口。
5. 固定实际版本，按原作者资料和最小场景核验；不能把“支持4.x”当成本项目验证通过。
6. 不自研寻路、碰撞、动画混合、WebSocket、通用状态图编辑器或测试框架。
7. 不为未来创建空接口、工厂、注册中心、通用DSL或无实际用途的配置。
8. 只在真实复用、外部边界或测试隔离需要时抽象；薄适配层不要套多层。
9. Godot主控空间与单步动作，Python主控目标、完整技能、会话和长期记忆，禁止双主控。
10. 不增加安全治理、重放、容灾、分布式、审计等非主线工作。
11. 不以简化为由删除记忆、状态、暂停、多人对象区分、动作反馈和实际模型接入。
12. 一次任务连通一个可见行为，只改必要文件，不顺手重构整个工程。
13. 插件无关功能不启用，不同时保留两套相机、状态或对话流程控制。
14. 交付说明实际改动、采用来源、自写缺口、执行验证及未完成项，禁止虚报运行结果。
```

**最终标准：用尽可能少的新机制完成全部主线体验，而不是用尽可能少的功能掩盖尚未完成的系统。**
